# Surface contract: bounded Pi goals

## Boundary and ownership

`pi-ad-goal/` is the standalone first-party Pi extension for one explicitly opted-in, bounded goal per active session branch. It registers `/goal`, model-callable goal tools, branch restoration, and continuation at Pi's public agent settle event. It is included in the canonical `pi-plugins` package. Operator-facing help, command feedback, and tool-authored explanations are in English; goals, progress, and user replies remain user data and are preserved. Declarative hooks are separately owned by `pi-ad-hooks`.

## Inputs and behavior

- `/goal <goal>` starts a goal; `/goal start <goal>` is an explicit form for goals beginning with reserved management words. `/goal` with no arguments shows help. `/goal status`, `pause`, `resume [answer]`, `limit <N|off|default>`, `done`, and `stop` inspect/control the goal. Each goal defaults to a limit of 40 automatic continuations; `off` makes it unlimited and `default` restores 40.
- A model-callable `goal_control` tool carries out clear operator requests to start/status/pause/resume/done/stop. A start requires an explicit operator request; the assistant can suggest goal mode for substantial scope but must wait for agreement. `goal_update` records progress, done, or blocked states. The bundled goal-workflow skill says to report state changes only after tool confirmation and to mark a goal done only when it is complete.
- Exactly one goal may be nonterminal on a branch. A new start is refused until the current goal is stopped or terminal. Goal transitions are validated by the extension.
- After a completed run, an active goal receives one hidden continuation until its per-goal limit is reached. Failed/aborted runs pause it. The default is 40; `off` disables the limit. `/goal resume [answer]` resets continuations used to zero and begins a new continuation cycle. Session load/tree navigation restores state but never starts background work.
- Background subagents: when an active goal's run completes, the extension asks the bundled pi-subagents for the number of this session's running subagents through its documented in-process RPC (`status`, `data.fleet.totalActive`, 1.5 s timeout). If any are running, no continuation is injected and no step is counted; the goal stays active and `/goal status` reports how many it waits for. Any run start (normally pi-subagents' completion wake) ends the wait, and that run's settle decides again. After a `subagent:async-complete` event, if no run started within 2 s, Pi is idle, and none are running, the goal injects one continuation itself (counted against the limit). While subagents run, `goal_update action=done` is refused with an instruction to wait for their results; operator `/goal done` and `goal_control done` are not restricted. If pi-subagents does not answer, the goal behaves as without it and stops asking until a pi-subagents event is seen.
- Review rejection limit: within one goal cycle (since start or the latest resume), after 2 reviewer verdicts requesting changes the next settle blocks the goal, notifies the operator, and injects one final hidden instruction to stop delegating (no new/resumed/steered workers or reviewers, no PR open/merge) and report outstanding findings, per-round fixes, current state, active background runs, and options. A reviewer result is a completed pi-subagents notice naming `**reviewer**` (single `Background task completed:`, batched `Background tasks completed (N):`, or `Detached foreground task completed:`; a grouped notice is split into `N. reviewer` blocks) or a top-level `subagent` tool result whose call targeted `agent: "reviewer"`; each counts at most once. Its verdict is the last `Merge verdict: BLOCK|OK` line (the stock reviewer format; `BLOCK` is a rejection), otherwise the first review heading carrying `REQUEST_CHANGES` or `APPROVE` within the following 400 characters. When the text has no verdict but carries pi-subagents' `Full output: <path> (…). Read it if needed.` reference, the verdict is read from that regular file (at most 1 MiB) and recorded as a `pi-ad-goal-review-verdict` custom entry `{ path, rejected }`, so the count survives restarts and file cleanup. Failed runs, chain/parallel calls, assistant/user text, status/transcript views, and unreadable files are not counted (they can only delay the block; the continuation limit still applies). The branch count at cycle start is persisted as `reviewRejectionBaseline`; a legacy state without it starts counting at its next settle. In-flight subagent runs are not cancelled.
- `/cancel` remains Pi's current-operation cancellation. An aborted active goal is paused. `/goal stop` closes the goal and frees the single-goal slot but does not cancel an in-flight Pi operation.
- `/goal status`, `pause`, `limit`, `done`, and `stop` may be used while a Pi operation is in progress. Status is observational; pause/limit/done/stop affect goal state and future continuation only. Their feedback must make clear when the current operation continues. In particular, while an operation is busy, `/goal stop` must tell the operator to wait before starting another goal. Slash-command `/goal start` and `/goal resume` require an idle session and are rejected rather than queued; `/cancel` is the way to abort current Pi work. A `goal_control` tool call made during the current run is not a separate queued slash command and retains its explicit-operator-consent rule.

## Persistence and compatibility

Goal state, including its per-goal continuation limit, is stored in custom session entries and reconstructed from the active branch. A missing limit in an older state defaults to 40; numeric limits and `off` (unlimited) persist per goal. Status reports continuations used and the configured numeric limit or `unlimited`. Goals/progress remain model context. State is written as custom entry type `pi-ad-goal` (version-1 schema) and continuations as hidden custom messages of type `pi-ad-goal-continuation`. Entries of the pre-rename type `pi-ad-hooks-task` are still read, so sessions started with the former `/task` command (extension `pi-ad-task`) keep their goal; the next write uses the new type. Reviewer verdicts read from files are recorded as `pi-ad-goal-review-verdict`; the pre-rename `pi-ad-task-review-verdict` is still read. Unknown fields from earlier releases are ignored on load and dropped on the next write.

## Failure behavior

Goal-specific rejections explain a viable next action. The extension is local: besides pi-subagents status requests on the in-process event bus it emits no shared Pi events, and it sends goal state nowhere except the configured model.

## Security and non-goals

Goals and progress are persisted locally and sent to the configured model as ordinary goal context. The goal starts no workers of its own and sends no external notifications; it only queries the in-process pi-subagents API and reads reviewer output files that pi-subagents referenced on the branch. The extension supports one goal only: no multiple-goal list, IDs, or switching. The skill may suggest goal mode but may not autonomously start a goal.
