# Surface contract: bounded Pi tasks

## Boundary and ownership

`pi-ad-task/` is the standalone first-party Pi extension for one explicitly opted-in, bounded task per active session branch. It registers `/task`, model-callable task tools, branch restoration, and continuation at Pi's public agent settle event. It is included in the canonical `pi-plugins` package. Operator-facing help, command feedback, and tool-authored explanations are in English; goals, progress, and user replies remain user data and are preserved. Declarative hooks are separately owned by `pi-ad-hooks`.

## Inputs and behavior

- `/task <goal>` starts a task; `/task start <goal>` is an explicit form for goals beginning with reserved management words. `/task` with no arguments shows help. `/task status`, `pause`, `resume [answer]`, `limit <N|off|default>`, `done`, and `stop` inspect/control the task. Each task defaults to a limit of 40 automatic continuations; `off` makes it unlimited and `default` restores 40.
- A model-callable `task_control` tool carries out clear operator requests to start/status/pause/resume/done/stop. A start requires an explicit operator request; the assistant can suggest task mode for substantial scope but must wait for agreement. `task_update` records progress, done, or blocked states. The bundled task-workflow skill says to report state changes only after tool confirmation and to mark a task done only when its goal is complete.
- Exactly one task may be nonterminal on a branch. A new start is refused until the current task is stopped or terminal. Task transitions are validated by the extension.
- After a completed run, an active task receives one hidden continuation until its per-task limit is reached. Failed/aborted runs pause it. The default is 40; `off` disables the limit. `/task resume [answer]` resets continuations used to zero and begins a new continuation cycle. Session load/tree navigation restores state but never starts background work.
- Background subagents: when an active task's run completes, the extension asks the bundled pi-subagents for the number of this session's running subagents through its documented in-process RPC (`status`, `data.fleet.totalActive`, 1.5 s timeout). If any are running, no continuation is injected and no step is counted; the task stays active and `/task status` reports how many it waits for. Any run start (normally pi-subagents' completion wake) ends the wait, and that run's settle decides again. After a `subagent:async-complete` event, if no run started within 2 s, Pi is idle, and none are running, the task injects one continuation itself (counted against the limit). While subagents run, `task_update action=done` is refused with an instruction to wait for their results; operator `/task done` and `task_control done` are not restricted. If pi-subagents does not answer, the task behaves as without it and stops asking until a pi-subagents event is seen.
- Review rejection limit: within one task cycle (since start or the latest resume), after 2 reviewer verdicts requesting changes the next settle blocks the task, notifies the operator, and injects one final hidden instruction to stop delegating (no new/resumed/steered workers or reviewers, no PR open/merge) and report outstanding findings, per-round fixes, current state, active background runs, and options. A reviewer result is a completed pi-subagents notice naming `**reviewer**` (single `Background task completed:`, batched `Background tasks completed (N):`, or `Detached foreground task completed:`; a grouped notice is split into `N. reviewer` blocks) or a top-level `subagent` tool result whose call targeted `agent: "reviewer"`; each counts at most once. Its verdict is the last `Merge verdict: BLOCK|OK` line (the stock reviewer format; `BLOCK` is a rejection), otherwise the first review heading carrying `REQUEST_CHANGES` or `APPROVE` within the following 400 characters. When the text has no verdict but carries pi-subagents' `Full output: <path> (…). Read it if needed.` reference, the verdict is read from that regular file (at most 1 MiB) and recorded as a `pi-ad-task-review-verdict` custom entry `{ path, rejected }`, so the count survives restarts and file cleanup. Failed runs, chain/parallel calls, assistant/user text, status/transcript views, and unreadable files are not counted (they can only delay the block; the continuation limit still applies). The branch count at cycle start is persisted as `reviewRejectionBaseline`; a legacy state without it starts counting at its next settle. In-flight subagent runs are not cancelled.
- `/cancel` remains Pi's current-operation cancellation. An aborted active task is paused. `/task stop` closes the task and frees the single-task slot but does not cancel an in-flight Pi operation.
- `/task status`, `pause`, `limit`, `done`, and `stop` may be used while a Pi operation is in progress. Status is observational; pause/limit/done/stop affect task state and future continuation only. Their feedback must make clear when the current operation continues. In particular, while an operation is busy, `/task stop` must tell the operator to wait before starting another task. Slash-command `/task start` and `/task resume` require an idle session and are rejected rather than queued; `/cancel` is the way to abort current Pi work. A `task_control` tool call made during the current run is not a separate queued slash command and retains its explicit-operator-consent rule.

## Persistence and compatibility

Task state, including its per-task continuation limit, is stored in custom session entries and reconstructed from the active branch. A missing limit in an older state defaults to 40; numeric limits and `off` (unlimited) persist per task. Status reports continuations used and the configured numeric limit or `unlimited`. Goals/progress remain model context. The version-1 entry schema, custom entry type `pi-ad-hooks-task`, and continuation message type `pi-ad-hooks-task-continuation` are retained across extraction so existing transcripts remain readable. Unknown fields from earlier releases are ignored on load and dropped on the next write.

## Failure behavior

Task-specific rejections explain a viable next action. The extension is local: besides pi-subagents status requests on the in-process event bus it emits no shared Pi events, and it sends task state nowhere except the configured model.

## Security and non-goals

Task goals and progress are persisted locally and sent to the configured model as ordinary task context. The task starts no workers of its own and sends no external notifications; it only queries the in-process pi-subagents API and reads reviewer output files that pi-subagents referenced on the branch. The extension supports one task only: no multiple-task list, IDs, or switching. The skill may suggest task mode but may not autonomously start a task.
